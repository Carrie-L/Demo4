## 1. 本次已经确定的规则

| 编号 | 最终规则 |
|---|---|
| R01 | A 为常用工具组件引导，B 为 AI 快看组件引导 |
| R02 | A、B 各自累计最多展示 3 次；不存在第四次 |
| R03 | thirdPopInterval 无论有没有、配置多少，都不参与展示判断 |
| R04 | 同类型第 1 次后等待 firstPopInterval 个固定 24 小时；第 2 次后等待 secondPopInterval 个固定 24 小时 |
| R05 | A、B 分别记录次数、上次展示时间、点击添加后的停止状态 |
| R06 | A、B 另外共用“本地自然日合计最多展示 1 次”的限制 |
| R07 | 每一轮必须重新完成有效行为并沿原页面栈返回；一轮只有一次即时评估机会 |
| R08 | 因冷却、当日额度、云配、宿主不可展示等原因没有展示，这一轮机会结束，不保留资格 |
| R09 | 冷启动仅进入首页不触发；重启不恢复上一进程的行为资格 |
| R10 | 点击弹窗任意添加按钮，立即永久停止该类型；deeplink 打开失败也停止；另一类型不受该点击影响 |
| R11 | 点击空白取消不会永久停止，但已经展示的次数和当天额度不会退回 |
| R12 | 设置页手动添加只对荣耀设备显示；不经过自动弹窗，也不改变 A/B 的次数或停止状态 |
| R13 | 自动弹窗 A/B 不受“仅荣耀”条件限制 |
| R14 | 数据保存在本地 SP/MMKV；用户清除应用全部数据后重新开始 |
| R15 | Kotlin + XML；继续使用项目原有 ARouter 和快服务 deeplink |

**“独立”与“共享”同时存在：** A 达到 3 次或点击添加，只停止 A；B 可以在自己的有效流程返回时继续判断。但今天 A 已经展示，会通过共享日额度阻止今天再展示 B。点击 A 不会把 B 标记为永久停止。

**不会设置到期弹窗计时器。** 时间到了只意味着“下次新行为返回时可能通过频控”，不意味着坐在首页等到时间就突然弹出。

## 2. 页面结构和 UI 接入点

这些页面是现有产品业务页面。正式集成时在原页面增加事件接入，不要求为这个功能重做搜索/资讯业务；验证工程可用 Kotlin + XML 模拟对应结构。

| 页面 | UI 与入口 | 实际目标 | 本功能如何识别 |
|---|---|---|---|
| 首页推荐频道 | 顶部普通搜索框 | 搜索激活页 | 开始首页搜索流程，尚未完成关键节点 |
| 首页推荐频道 | 搜索按钮 | 搜索结果页 | 实际进入结果页后标记搜索关键节点 |
| 首页推荐频道 | 搜索框高亮暗词 | 由 deeplink 决定，可能结果页或资讯详情 | 以实际业务落地页为准，不能仅凭点击暗词判定搜索成功 |
| 首页推荐频道 | 搜一扫按钮 | 扫一扫页 | 实际进入后，沿原栈返回可触发 A；不要求扫码成功 |
| 搜索激活页 | 搜索框、搜索按钮 | 提交后进入搜索结果页 | 只有本次流程来自首页，且实际进入结果页才有效 |
| 搜索激活页 | 搜索历史、猜你想搜 | 搜索结果页 | 同上，入口类型用于区分和调试 |
| 搜索激活页 | 横向热搜榜 ViewPager：游戏、电影电视、综艺、视频 | 电影电视/综艺 item 到结果页；游戏/视频到其他页 | 用真实目标类型判断，不用榜单位置猜测 |
| 首页 AI 快看频道 | AI 资讯列表 item | 资讯详情页 | 开始 B 的首页来源流程 |
| 我的页 | 书签、历史、下载 | 书签历史容器或下载页 | 开始 A 的我的来源流程 |
| 书签历史容器 | 左书签、右历史两个 Tab | 同一个 Activity 内切换 | 是容器内部状态变化，不是两个 Activity 的压栈/出栈 |
| AI 搜页 | AI 快看入口 | AI 快看二级列表页 | 记录二级页确实来自 AI 搜；到达列表本身不触发 B |
| AI 快看二级列表页 | 资讯 item | 资讯详情页 | 开始 B 的二级页来源流程，回到该二级页才评估 |
| 设置页 | 添加桌面组件列表项 | 快服务添加界面 | 荣耀设备显示，点击直接 deeplink，不调用自动引导流程 |

首页与我的共用 Activity。识别承载位置时必须同时知道底部 Tab 和首页频道，不能只判断 MainActivity 是否 onResume。

### 2.1 建议 XML 构成

- 首页验证布局：顶部搜索区域（搜索框、搜索按钮、扫一扫按钮）+ 频道 Tab + 对应列表。
- 搜索激活布局：搜索区域 + 历史列表 + 猜你想搜列表 + 榜单 Tab + 横向 ViewPager2；各榜单页用 RecyclerView。
- 书签历史布局：TabLayout + ViewPager2，两个 Fragment 共用一个业务容器身份。
- AI 首页/二级页：各自的 RecyclerView 列表，不能混用页面实例或返回宿主。
- 引导弹窗：一个复用 XML 布局，由 A/B 内容提供者注入标题、截图和两条 deeplink。
- 设置列表：由 DeviceClassifier 决定是否包含添加组件 item，而非仅隐藏图标留下空行。

上述控件是实现建议，不引入新的产品规则。现有项目已经有对应组件时，直接接入原组件。

## 3. 每类流程的判定

“关键节点”表示用户已经做过对应业务动作；“返回点”表示现在有一次评估弹窗的机会。这两者必须分开记录。

| 流程 | 合法起点 | 关键节点 | 必须返回到 | 弹窗位置 |
|---|---|---|---|---|
| A：首页搜索 | 首页推荐的搜索入口 | 本次路径中的搜索结果页 | 原首页承载实例 | 首页非 AI 频道底部 |
| A：我的工具 | 原我的页的书签/历史/下载入口 | 对应工具容器实际进入 | 原我的页 | 我的页底部 |
| A：扫一扫 | 首页扫一扫入口 | 扫一扫业务页实际进入 | 原首页承载实例 | 首页非 AI 频道底部 |
| B：首页资讯 | 首页 AI 频道资讯 item | 对应资讯详情页 | 原首页 AI 频道 | 首页 AI 频道底部 |
| B：二级页资讯 | 从 AI 搜进入的 AI 快看二级页 item | 对应资讯详情页 | 原 AI 快看二级页实例 | 该二级页底部 |

A 的三个来源共用 A 的 3 次和冷却，不是每个来源各 3 次。B 的两个来源共用 B 的 3 次和冷却。

### 3.1 首页搜索逐例解释

| 路径 | 是否产生本轮评估机会 | 原因 |
|---|---|---|
| 首页 → 结果 → 原栈返回首页 | 是 | 有搜索结果关键节点 |
| 首页 → 激活 → 结果 → 激活 → 首页 | 是 | 合法搜索分支完整返回 |
| 首页 → 激活 → 首页 | 否 | 没有实际进入结果 |
| 首页 → 激活 → 游戏/视频 → 激活 → 首页 | 否 | 非搜索结果分支不满足关键节点 |
| 首页 → 激活 → 历史/猜你想搜/影视综艺 item → 结果 → 若干页 → 逐层返回结果、激活、首页 | 是 | 结果出现后允许继续浏览，返回链完整 |
| 首页暗词 → 结果 → 首页 | 是 | 实际落地为搜索结果 |
| 首页暗词 → 资讯详情 → 首页 | 否 | 普通详情不是搜索结果，也不是 AI 频道来源 |
| 首页 → 激活 → 游戏 → 游戏内部打开的结果 → 逐层返回首页 | 否 | 该结果不是首页指定搜索分支直接产生，不能借用祖先来源 |
| 其他页面 → 激活 → 结果 → 首页 | 否 | 缺少首页发起的有效流程 |
| 首页 → 结果 → 其他页 → 按“首页”按钮清栈回首页 | 否 | 不是沿原页面栈返回 |
| 首页 → 结果 → 杀进程 → 冷启首页 | 否 | 行为流程不跨进程恢复 |

一个技术处理约定：从激活页先打开游戏，再原栈返回同一激活页后重新点击一个合法搜索入口，并实际到结果页，可以基于这次新的合法搜索分支满足节点；之前的游戏分支本身永远不授予资格。不能把“经历过一个游戏页”误记成搜索，也不能把“重新进行了合法搜索”永久封死。

### 3.2 书签/历史共 Activity 的处理

例如：我的 → 书签历史 Activity（书签 Tab）→ 切历史 Tab → 打开网页 → 返回历史 Tab → 返回我的。

只记录一次进入书签历史容器，切 Tab 不增加页面栈层级，不重复授予行为。网页离开和返回属于该容器之上的子页面。容器正常结束并回到原我的页，产生一次 A 评估机会。

不能把 tabSelected 回调当成“从我的进入历史”，否则横向滑动会被当作新一轮工具访问。

### 3.3 两种 AI 场景的差别

首页 AI 流程的承载页是首页 AI 频道；二级 AI 流程的承载页是从 AI 搜进入的那一个二级页。

进入 AI 搜、进入 AI 二级列表都不直接完成资讯访问。点击资讯并回到二级页时才产生 B 的机会。继续从二级页返回 AI 搜，不再产生一次 B；从其他入口打开的无有效来源二级页，也不能借用另一个二级页的流程。

## 4. 先用一次真实行为理解整个系统

以“首页 → 搜索激活 → 搜索结果 → 网页 → 返回结果 → 激活 → 首页”为例：

1. 首页发起跳转时，创建一个只存在内存中的 FlowSession。它代表“这一次出去做事再回来”。
2. 到激活页时，流程继续，但 qualified 仍为 false。
3. 从这个激活页的合法搜索入口实际进入结果页，将本流程 qualified 设为 true。
4. 继续去网页时，把真实的新页面记录到本流程的返回路径；qualified 不因为正常继续浏览而变回 false。
5. 用户返回时，核对是不是从路径栈顶回到它的直接父页面，逐层减少路径。
6. 最后回到原首页，且首页真正可见、处于非 AI 频道，生成一个一次性 ReturnAttempt。
7. 立即消费这次 ReturnAttempt，检查开关、A 的状态、共享日额度和 A 冷却。
8. 符合则尝试立刻显示；不符合则结束。本次搜索的资格不会留到之后。
9. 下一次想弹 A，必须重新开始一轮有效流程。重复 onResume、时间到期、云配更新都不能复活第 6 步的机会。

FlowSession 只回答“这次流程是否完整”；SP/MMKV 回答“这个类型过去弹了几次，是否已点击添加停止”。两者不能混存。

## 5. 模块结构和职责

~~~mermaid
flowchart TD
    Page["现有页面与 ARouter 适配"] --> Flow["FlowTracker：本次行为和原栈返回"]
    Flow --> Attempt["一次性 ReturnAttempt"]
    Attempt --> Controller["Controller：串行评估与展示"]
    Controller --> Policy["Policy：云配、类型频控、共享日额度"]
    Controller --> Store["Repository：SP / MMKV"]
    Controller --> Host["Host：底部弹窗与当前页面"]
    Host --> Controller
~~~

| 模块/拟议类 | 做什么 | 为什么单独拆分 |
|---|---|---|
| GuideNavigationAdapter | 把现有路由、页面可见和正常返回转换成可信业务事件 | 不让核心逻辑依赖 ARouter 的具体 API |
| GuideFlowTracker | 识别本轮关键节点，核对原页面栈返回 | 不把“进入过结果页”误当长期资格 |
| GuideReturnCoordinator | 连接返回事实与承载页本次恢复可见 | 返回回调可能早于可以展示 UI 的时刻 |
| GuideFrequencyPolicy | 纯函数判断这一次是否允许展示 | 单测不需要 Activity、SP 和真实等待 |
| WidgetGuideController | 串行处理返回、写盘、首帧、点击与关闭 | 防重复弹窗和并发日额度竞争 |
| GuideRepository | 原子地读改写完整状态，管理记录与停止标记 | A/B 日额度和点击停止需要一致存储 |
| GuideConfigSource | 提供已校验的配置快照 | 云配 SDK、缓存和网络与规则解耦 |
| GuideHost | 检查页面状态并同步接受/拒绝一次展示 | 对接项目统一弹窗管理器 |
| WidgetGuideBottomDialog | XML 底部弹窗，报告首帧/添加点击/取消 | UI 不自行改次数或云配 |
| WidgetGuideNavigator | 打开快服务 deeplink | 明确“发起跳转”不等于“添加成功” |
| DeviceClassifier | 为设置页提供 isHonorDevice | 品牌限制不会误加到自动引导 |

这些是拟议边界，最终可按正式工程包结构合并文件，不要求为每个简单对象新建模块。

## 6. 内存模型：把身份、行为和返回分清楚

本节结构用于解释实现，不是现有 V1 源码的实际定义。

### 6.1 类型与字段字典

| 对象 | 字段 | 含义 |
|---|---|---|
| PageIdentity | processSessionId | 当前进程启动时生成的随机标识；拒绝上个进程残留事件 |
| PageIdentity | taskId | Android 任务栈标识，只做隔离，不能单独当页面 ID |
| PageIdentity | containerId | Activity 或真正有独立返回栈的 Fragment/业务页面实例标识 |
| PageIdentity | pageKind | 实际业务页面类别，如 SEARCH_RESULTS、SCAN、AI_SECONDARY |
| PageIdentity | surface | 当前展示位置，区分首页非 AI、首页 AI、我的、二级 AI |
| FlowSession | flowId | 本次外出流程的 ID；一轮内多次页面跳转仍属于同一个流程 |
| FlowSession | guideType | 最终可能展示 A 还是 B |
| FlowSession | triggerKind | HOME_SEARCH、MINE_TOOL、HOME_SCAN、HOME_AI_NEWS、SECONDARY_AI_NEWS |
| FlowSession | owner | 本轮最终必须返回的承载实例与位置要求 |
| FlowSession | entryChildId | 承载页本次直接打开的子页面实例 |
| FlowSession | path | 本流程已确认的页面父子关系及当前尚未返回的路径 |
| FlowSession | qualified | 本轮是否已实际到达合法关键节点；不是永久资格 |
| FlowSession | milestonePageId | 授予关键节点的具体实例，用于定位和防串线 |
| FlowSession | valid | 是否仍能证明沿原栈正常返回；清栈/跨任务/未知重定向会使它失效 |
| ReturnAttempt | attemptId | 一次返回评估的 ID，重复回调只能消费一次 |
| ReturnAttempt | flowId | 来自哪一轮流程 |
| ReturnAttempt | owner | 本次返回到哪个承载实例 |
| ReturnAttempt | visibilityGeneration | 本次返回产生的可见版本，后续离开再回来不能复用 |
| ReturnAttempt | guideType | 只评估指定类型，不转成其他弹窗的候选 |
| HostSnapshot | resumed、topVisible、stateSaved | 页面是否真正可承载 UI、是否被业务页覆盖、Fragment 是否已保存状态 |

三个 ID 的区别：

- navigationId：一次具体导航动作，例如从激活页到结果页。
- flowId：从首页出发到回到原首页的整轮过程，包含多次导航。
- attemptId：这轮返回时唯一的一次评估机会。

presentationId 是第四种 ID：只在确实准备展示时生成，用于展示次数和点击/关闭回调去重。不要让一种 ID 同时承担所有职责。

### 6.2 拟议 Kotlin 数据形状

~~~kotlin
/** 只存在内存：用于这一轮返回判断，绝不写入 SP。 */
data class ReturnAttempt(
    val attemptId: String,
    val flowId: String,
    val processSessionId: String,
    val ownerContainerId: String,
    val visibilityGeneration: Long,
    val guideType: GuideType
)

/** 只负责限定允许展示的位置，不替代页面实例校验。 */
enum class GuideSurface {
    HOME_NON_AI, HOME_AI, MINE, AI_SECONDARY, NONE
}

/** 五个触发来源，最终只归入 A/B 两套频控。 */
enum class TriggerKind {
    HOME_SEARCH, MINE_TOOL, HOME_SCAN,
    HOME_AI_NEWS, SECONDARY_AI_NEWS
}
~~~

命名是实现建议。需要写 KDoc 解释每个字段代表“动作”“实例”还是“本轮流程”，避免再次出现只有字段名、无法看懂关联关系的问题。

### 6.3 状态机

~~~mermaid
stateDiagram-v2
    [*] --> Idle
    Idle --> Tracking: 合法入口发起并实际进入目标
    Tracking --> Qualified: 实际进入本轮关键节点
    Tracking --> Ended: 未满足节点就返回承载页
    Qualified --> Qualified: 正常浏览子页面并逐层返回
    Tracking --> Invalid: 跳栈或来源不可信
    Qualified --> Invalid: 跳栈或来源不可信
    Qualified --> Attempt: 原栈回到指定承载页并恢复可见
    Attempt --> Presenting: 立即频控通过且宿主接纳
    Attempt --> Ended: 任一条件不满足
    Presenting --> Ended: 首帧计次后取消或点击添加
    Invalid --> Ended: 丢弃流程
    Ended --> [*]
~~~

频控失败的 Attempt 不会回到 Qualified。云配更新、时钟更新、回前台均没有从 Ended 重新弹出的转换。


### 6.4 多个来源流程如何共存

流程按 processSessionId、taskId、ownerContainerId 和 flowId 关联，不使用全局一个 fromHome 或 hasSearched 布尔值。同一个承载页的一笔外出请求只拥有一轮；新的不兼容导航使旧轮失效。

如果用户在一个尚未返回首页的流程里，又从合法 AI 二级页打开资讯，可以有属于二级页的内层 B 流程。它只在回到该二级页时评估 B；外层路径仍按真实压栈/出栈记录，不借用内层的关键节点。若 B 先显示，之后外层 A 回到首页时会因共享日额度被拒绝并结束。

跟踪器可有多笔内存流程，但展示事务全进程只有一笔。已结束、失效或宿主永久移除的流程及时清理，避免持有 Activity 和无界增长的历史路径。

## 7. 怎样证明“沿原页面栈返回”

### 7.1 不能仅靠下面三个信号

| 信号 | 能证明什么 | 不能证明什么 |
|---|---|---|
| onResume | 某个 Activity 恢复了 | 是否由本轮返回引起、当前 Tab 是否正确、是否刚冷启动 |
| onActivityResult / Promise 完成 | 某个请求回调了 | 是否经过搜索结果、是否逐层返回、是否仍是原承载实例 |
| ARouter onArrival | 路由已执行到启动阶段 | 用户已经完成行为、更不能表示已经返回 |

因此事件必须有“从哪里来、去了哪里、如何回来”的关联。

### 7.2 推荐：在现有路由适配层维护本流程的返回关系

不读取整个系统任务栈、不使用隐藏 API，也不新建一个替代 ARouter 的路由框架。只对**处于活动引导流程中的相关路径**维护轻量的实例父子关系。

拟议事件：

| 事件 | 产生位置 | 处理 |
|---|---|---|
| RouteRequested | 项目统一路由封装 | 记录来源、入口、候选目标和 navigationId；尚不授予关键节点 |
| PageEntered | 最终业务页真实进入 | 确认实际类型，登记父子边；合法直接目标才授予节点 |
| NormalReturnRequested | 已提交的返回操作适配处 | 标记准备返回直接父实例；取消的预测返回手势不产生完成事实 |
| ParentVisibleAfterReturn | 原父页面恢复可见且返回关系确认 | 与前一条配对后弹出一层路径 |
| ContainerTabChanged | 书签历史容器等 | 更新内部位置，不当作入栈或出栈 |
| StackReplaced / RouteReusedUnexpectedly | CLEAR_TOP、重排、跨任务或不符合本流程的复用 | 使受影响流程失效 |
| HostDestroyed / ProcessChanged | 生命周期/进程容器 | 清理或拒绝过期身份，配置重建另行处理 |

路由失败、被拦截且没有实际落地，不能当作进入关键节点。短暂的透明中转 Activity 要由适配层明确标记为路由实现细节；最终业务页确认后再建立业务导航边，不能用中转 onArrival 猜实际目标。

### 7.3 深层返回的具体核对

假设实际路径依次为 H（首页）、S（激活）、R（结果）、D1、D2：

- D2 正常返回 D1：核对栈顶 D2 和直接父 D1，确认后弹出 D2。
- D1 正常返回 R：确认后弹出 D1；搜索关键节点保留。
- R 正常返回 S：确认后弹出 R。
- S 正常返回原 H：完成整轮，交给 ReturnCoordinator。
- D2 直接打开或清栈回 H：不是本路径的一次直接父返回，整轮失效，即使最终 H 的 onResume 被调用也不弹。

一旦本轮检测到跳栈，其后迟到的结果回调不能使流程重新有效。

### 7.4 如何接入“其它若干页”

必须覆盖本流程中途页面的真实进入与返回。可以利用项目已有 BaseActivity/页面栈管理器/统一路由封装，减少每个业务页的接入量，但不能宣称“只改首页 onResume”就能准确核验所有路径。

如果中间页面绕过路由封装，则需要它通过公共页面接入层报告。如果无法可靠观测某一步，本轮按无法证明完整返回处理，不猜测为成功。

Fragment、WebView 内的业务返回栈也可能属于“其它若干页”。如果这些业务页具有独立返回语义，就接入该栈的 push/pop；不能只凭外层 Activity 的回调证明其内部路径。普通网页内点击但不形成产品定义的页面层级，可由业务适配器归为同一个容器状态。

### 7.5 生命周期、旋转和进程

- 同一进程的配置重建：可保留流程；containerId 使用可恢复的逻辑实例 ID，绑定新的 Activity 对象。onDestroy 且 isChangingConfigurations 不当成用户返回。
- 进程重启：processSessionId 改变，内存流程不存在。即使 Bundle 恢复了页面 ID、系统补发结果，也没有可用 flowId，不能触发。
- 中途切到后台再回来：不产生返回评估；尚未完成的同进程流程可以继续。真正按原栈回来才评估。
- 已回到承载页但还没显示就切后台：丢弃本次机会，恢复前台不补弹。
- 预测返回手势开始后取消：不弹栈、不生成返回机会。
- 多窗口：按 taskId 和实例区分路径；展示还要满足项目对顶层可交互宿主的判断，不能只看 RESUMED。

### 7.6 “等页面恢复”与“保留资格”的界限

正常返回结果可能早于父页面完成生命周期恢复。允许 ReturnCoordinator 把**这一笔返回事实**交给紧接着的同一承载页恢复事件；此时还未生成 ReturnAttempt，不属于长期等待冷却。

配对后生成 ReturnAttempt 并立即处理：

- owner、processSessionId、返回事务、visibilityGeneration 必须匹配；
- 父页在这次返回后实际可见、处于允许的位置；
- 一旦切 Tab、离开、进入后台、出现新的导航、恢复到了其他实例，配对作废；
- 不为未就绪的弹窗管理器排队，不等待云配拉取成功，不等待冷却；
- 单次系统恢复过程完成后仍无法安全展示就结束，不能挂一个“下次 onResume 再试”的标记。

## 8. ARouter、Activity Result 和 Promise 的方案选择

### 8.1 可以保留 ARouter

现有代码不需要全部改成直接调用 startActivityForResult。ARouter 的 requestCode 重载能发起带结果请求：导航时传当前 Activity 和 requestCode，结果由原 Activity 接收。这个重载和业务链路跟踪可以配合使用。[S1]

~~~kotlin
// 用于解释既有 ARouter 的结果跳转方式，不是本轮新增业务代码。
ARouter.getInstance()
    .build("/search/activate")
    .navigation(this, REQUEST_GUIDE_SEARCH)
~~~

实际路由地址使用正式项目现有配置。不要直接假设普通 navigation() 返回 Future，也不要将 onArrival 放进“返回后弹窗”的位置。

### 8.2 推荐方案与可选方案

| 方案 | 接入方式 | 对本需求的适合程度 |
|---|---|---|
| 保留 ARouter 普通跳转 + 本轮路径跟踪 + 返回可见配对 | 页面真实进入/返回交给统一协调器 | 推荐作为业务核心；也能覆盖同 Activity 的 Tab/Fragment |
| ARouter requestCode + onActivityResult | 原直接子页结束时通知父页，再由同一协调器核对 flowId、关键节点、返回路径 | 可用于已经采用结果跳转的页面，不能替代路径判定 |
| AndroidX Activity Result + ARouter 适配 | 路由解析与发起通过项目桥接，结果回调交给协调器 | 新增结果基础设施时优先考虑；不为本功能强制升级全项目 |
| 项目已有 Future/Promise 封装 | thenAccept 把结果转交协调器 | 审核封装后可复用，不能假设 API 名字代表正确返回语义 |

正式实现只选一条路径作为“返回事实”的主要来源；如果生命周期和结果回调同时接入，按 returnId/attemptId 去重，不能各自调用一次 show。

### 8.3 为什么只监听最初子页面还不够

首页启动搜索激活页后，返回结果只直接关联搜索激活页。激活页内部是否进入了结果、是否经过异常清栈，需要：

- 由统一 FlowTracker 已经记录；结果回调只通知“现在可以核对返回”，或
- 由结果页向激活页回传明确的本轮结果，激活页再传回首页，并额外校验实际返回关系。

不能将任意 RESULT_OK 当作“搜索完成”；它可能是其他业务设置的结果。用户按 Back 返回也不保证每个页面主动设置 RESULT_OK。推荐使用独立的 guideFlowId/返回原因，业务结果码保持原有语义。

即使子页 setResult 了“搜索到过结果”，仍不能单靠这个字段证明 D2 没有 CLEAR_TOP。严格原栈要求必须有路径或现有页面管理器提供的可信返回证据。

### 8.4 thenAccept 的处理原则

原生 startActivityForResult 返回 void，没有 thenAccept。你提供的调用是项目或第三方封装，当前没有其定义，方案不依赖它的未知行为。[S2]

审核该封装时检查：

1. Promise 是启动成功就完成，还是目标结束后才完成？
2. 结果成功/取消是否都会回调？是否误把 Back 当异常而丢失正常返回？
3. 回调在哪个线程？操作 Controller/弹窗必须切回主线程。
4. requestCode 是否冲突？并发请求如何关联 flowId？
5. Activity 旋转或销毁时，闭包是否仍持有旧 Activity？
6. 进程重启补发结果时，是否会误恢复旧机会？
7. 原栈被清除、singleTask 复用时，是成功、取消还是永不完成？
8. callback 与 onResume 的先后次序是否被正确交接？

因此将来即使用 thenAccept，也只执行“交给返回协调器核验”，不直接写“promise 完成就 showDialog”。

### 8.5 AndroidX 版本边界

Android 官方建议新结果接口使用 Activity Result API，并要求稳定注册回调；其结果恢复能力不等于本业务必须恢复弹窗资格。[S3]

已核对 ARouter 官方开发分支存在调用方 launcher 适配能力，但开发分支 API 不能直接当作仓库当前 1.5.2 的可用 API。正式方案对现有版本使用已具备的 requestCode 能力或本轮事件跟踪；若需要现代 launcher 桥接，先核对实际依赖/项目封装，不写一个未验证的“ARouter.navigation(launcher)”调用。

本次不强制升级 ARouter，也不要求用户先提供 Promise 定义才可以理解或评审整体方案。

## 9. 云配、次数和每日额度

### 9.1 配置解释

~~~json
{
  "browserWidgetGuideRules": {
    "enable": true,
    "firstPopInterval": 1,
    "secondPopInterval": 10,
    "thirdPopInterval": 30
  }
}
~~~

| 字段 | 处理 |
|---|---|
| enable | 是否允许本次自动展示；缺失/非法时按关闭处理 |
| firstPopInterval | 同类型第 1 次展示到第 2 次展示的最短间隔，按 24h 计算 |
| secondPopInterval | 同类型第 2 次展示到第 3 次展示的最短间隔，按 24h 计算 |
| thirdPopInterval | 兼容接收但不参与规则；不允许由此产生第四次 |
| 旧字段 enablePop | V2 不把它当新字段；正式云配同步改为 enable，缺少 enable 时不擅自启用 |

1/10/30 是配置示例，不把产品给出的示例值误写成无法更新的常量。**3 次上限是本功能固定规则，不由 thirdPopInterval 决定。**

first/second 必须为非负整数，并在天数转毫秒时检查溢出。开启状态下缺失必要间隔或类型错误，整份规则按不可用处理，不猜测为零。关闭时可以直接关闭，不依赖间隔完整。third 不参与计算，因此其缺失或非预期内容不应改变前 3 次的判定。

配置刷新只替换配置快照，不主动生成 ReturnAttempt。网络失败是否沿用最近有效缓存，交给现有云配体系；本模块没有“加载完配置后补弹过去机会”的分支。

### 9.2 纯频控函数

前提：已经收到一个真实、尚未被消费的本轮返回机会。

~~~kotlin
// 说明判断顺序；并非完整可编译实现。
if (!config.enable) return Block(DISABLED)
if (type in stoppedTypes) return Block(ADD_CLICKED)
if (shownCount(type) >= 3) return Block(TYPE_LIMIT)
if (storageOrRecoveryBlocked(type)) return Block(RECOVERY)
if (!hostMatches(attempt)) return Block(HOST)
if (clockIsEarlierThanKnownHistory()) return Block(CLOCK_ROLLBACK)
if (anyRecordOnCurrentLocalDay()) return Block(SHARED_DAILY_LIMIT)

val count = shownCount(type)
val intervalDays = when (count) {
    0 -> null                    // 该类型首次不等待间隔
    1 -> config.firstPopInterval
    2 -> config.secondPopInterval
    else -> error("已由三次上限提前拒绝")
}
if (intervalDays != null &&
    nowMillis - lastShownAt(type) < intervalDays * DAY_MILLIS
) return Block(TYPE_COOLDOWN)

return Allow
~~~

乘法要先完成安全范围检查，示例省略解析实现。判断函数不写 SP、不清理流程、不打开窗口；控制器负责提前把 attempt 标记为已消费，再调用它。

first/second 都以**这个类型上一次真实展示时间**为基准。A 在首页、我的、扫一扫触发时都读取同一份 A 历史；B 两个展示位置也读取同一份 B 历史。

### 9.3 频次时间线

假设 enable=true，first=1、second=10，均使用同一时区：

| 时刻与操作 | 结果 |
|---|---|
| 10 月 11 日 09:00，第一次 A 有效返回 | A 第 1 次展示 |
| 当天 14:00，B 第一次有效返回 | 因共享当日额度拒绝；本轮 B 机会结束 |
| 10 月 12 日 08:00，再完成一轮 A | 距 A 上次不足 24h，拒绝；机会结束 |
| 当天 09:00，仍停留首页 | 不会自动弹 |
| 当天 09:05，重新完成一轮 A 并原栈返回 | A 第 2 次展示 |
| 当天 B 有效返回 | 仍被共享当日额度限制 |
| 10 月 13 日，B 重新完成有效流程 | 如无其他限制，B 第 1 次展示 |
| 10 月 22 日 09:05 后，A 新一轮有效返回，且当日无展示 | A 第 3 次展示 |
| 再过 30 天、300 天，A 新一轮有效返回 | 永不再展示 A；thirdPopInterval 完全不参与 |

每个类型最多 3 次，所以两个类型理论上合计最多 6 次，且受到共享每日限制；不是把旧的“AB 合计三次”保留下来。

### 9.4 两种时间口径

- 冷却：固定时间差，1 天=86,400,000 毫秒，10 天=240 小时。
- 每日额度：本地自然日，跨零点换日，不等于距上一弹窗已满 24h。
- 记录首帧当时的 wallTimeMillis、localEpochDay 和 zoneId；用同一个时间快照生成，避免跨零点取值不一致。
- 时间回拨或跨时区导致历史日期在“未来”时，保守拒绝这一次，不重置历史。使用设备时间不能保证防用户篡改。
- 时间恢复后也没有自动补弹；必须有新行为返回。
- 配置中 first/second 调整时，下次机会按新间隔与原真实展示时间计算，历史次数不变。

## 10. SP/MMKV 中保存什么

### 10.1 永久状态与临时状态严格分开

| 数据 | 保存位置 | 重启后是否保留 |
|---|---|---|
| A/B 真实展示记录 | SP/MMKV | 是 |
| A/B 点击添加停止标记 | SP/MMKV | 是 |
| 展示事务日志、异常恢复阻断 | SP/MMKV | 是，用于处理写盘和进程中断 |
| 本轮 flowId、页面路径、关键节点 | 进程内存 | 否 |
| ReturnAttempt、返回配对、宿主实例 | 进程内存 | 否 |
| 已完成过搜索/扫码的永久布尔值 | 不建立这种字段 | 不适用 |
| 设备是否荣耀 | 设备分类服务 | 不混入弹窗频控状态 |
| 云配缓存 | 现有云配模块 | 不与用户频次一并清写 |

因此不再保存 V1 的 behaviors 集合，更不会在启动时读取它来弹窗。

### 10.2 拟议持久模型

~~~kotlin
/** 一条真实首帧展示；最多正常产生 A 三条、B 三条。 */
data class ShowRecord(
    val presentationId: String,
    val guideType: GuideType,
    val shownAtMillis: Long,
    val localEpochDay: Long,
    val zoneId: String
)

/** 点击任意添加按钮的停止记录，不表示组件已经成功添加。 */
data class AddStopRecord(
    val guideType: GuideType,
    val presentationId: String,
    val target: AddTarget,
    val clickedAtMillis: Long
)

/** 整个状态作为一个 JSON 值写入，避免次数、日期、停止状态分裂。 */
data class PersistedGuideStateV2(
    val schemaVersion: Int,
    val records: List<ShowRecord>,
    val addStops: Map<GuideType, AddStopRecord>,
    val presentationJournal: PresentationJournal?,
    val recoveryHeldTypes: Set<GuideType>,
    val sharedQuotaUncertain: Boolean
)
~~~

次数从 records 按类型统计，上次展示时间从对应记录取最大值，共享日额度从所有 records 推导。不再单独存三份可能相互矛盾的 count、lastTime、lastDay。

recoveryHeldTypes/sharedQuotaUncertain 是异常保护，不是正常频控或已添加状态，详见第 12 节。正常数据里为空/false。

示意存储内容：

~~~json
{
  "schemaVersion": 2,
  "records": [],
  "addStops": {},
  "presentationJournal": null,
  "recoveryHeldTypes": [],
  "sharedQuotaUncertain": false
}
~~~

正式使用独立文件，例如 browser_widget_guide，单个 key 例如 state_v2。枚举与协议字段要有显式版本，不依赖反射字段名碰巧不被混淆。

### 10.3 SP 与 MMKV 的替换边界

拟议 StringStateStore 只提供 readWholeState / writeWholeState，Repository 在同一互斥区内完成读取、转换、编码和写入。

- SP：IO 线程调用 commit 并检查返回值；不在主线程执行磁盘操作，也不把 apply 当作已确认写盘。[S4]
- MMKV：复用项目现有实例/版本，单 key 存同一 JSON。按实际依赖版本核对 encode、同步和错误报告契约，不凭一个方法名承诺等同于数据库事务。[S5]
- 两者都使用主进程唯一仓库和控制器。单实例 Mutex 不能协调不同进程或别人绕过仓库直接改 key。
- 写入失败不能默认成功，读取损坏不能默认空记录。
- 清空应用全部数据后，记录、停止状态和恢复阻断都消失，按首次使用重新开始。
- 单独清缓存不是清应用数据，不能以此重置频次。
- 将该状态文件排除备份/设备迁移，防止用户清数据或重新安装后又被系统恢复历史；正式 app 其他备份策略保持项目原有设置。

## 11. 返回后的展示流程

### 11.1 只允许即时展示

~~~mermaid
sequenceDiagram
    participant Flow as 本轮流程跟踪器
    participant C as 返回与展示控制器
    participant R as 状态仓库
    participant H as 当前宿主
    participant UI as 底部弹窗
    Flow->>C: 原栈返回事实 + 本轮关键节点
    C->>H: 配对本次恢复可见
    C->>C: 生成并消费一次 ReturnAttempt
    C->>R: 读取状态，检查本次频控
    R-->>C: 当前历史与停止状态
    C->>C: 允许则准备唯一 presentationId
    C->>R: 持久保存 RESERVED 展示日志
    R-->>C: 写入成功
    C->>H: 重验实例、位置、配置和可见版本
    H->>UI: 同步接纳底部展示
    UI->>C: 首帧回调
    C->>R: 同 ID 写真实记录，日志转 SHOWN
    UI->>C: 取消或点击添加
    C->>R: 结束日志；添加则同时保存对应停止标记
~~~

图中仓库读取不一定每次重新访问磁盘：实现可在初始化成功后由唯一仓库维护已确认快照，但后续状态变化必须经过同一串行控制器，失败内存状态不能当成已持久数据。

### 11.2 逐步解释

1. **去重并消费机会。** 在启动 IO 前就标记 attempt 已消费，避免两个重复返回回调各自申请展示。
2. **判断类型。** 本流程只产生 A 或 B，不执行旧版 AI 页面上 B 不满足就补 A 的逻辑。
3. **检查全部规则。** 没有通过就结束流程，不创建 timer，不保留待弹队列。
4. **保存展示日志。** 这是恢复保护，不计入展示次数，也不是可跨进程恢复的行为资格。
5. **IO 返回后重新检查。** 当前宿主可能换页、切 Tab、进后台，云配也可能关闭；使用最新状态而非旧快照。
6. **同步争取弹窗名额。** 统一管理器忙则本轮结束。不得保存一个延迟到首页停留几分钟后再执行的 show 闭包。
7. **真实首帧才计次。** 用同一个 presentationId 去重；首帧时间决定记录时间及自然日。
8. **关闭后彻底结束。** 普通取消只清事务日志，点击添加还写停止状态。不能关闭后马上重试同一轮。

若写预约失败、展示被拒绝或第一帧前明确取消，这次没有展示记录，但 ReturnAttempt 已结束，下次仍须新行为。

### 11.3 宿主复核内容

- processSessionId、taskId、ownerContainerId 与本轮一致。
- 已恢复到当前顶层、可交互业务页面，Activity 不在 finishing/destroyed 状态。
- FragmentManager 可提交。
- 首页的底部 Tab/顶部频道组合正确；A 不在 AI 频道展示。
- B 二级页必须是原二级实例，不是后来新开的相同类页面。
- 当前 visibilityGeneration 仍是本次返回生成的版本。
- 此次写盘期间没有发生使请求失效的离开/后台/云配关闭，再恢复也不能复活。
- 共享展示名额仍属于当前 presentationId，没有其他类型抢占。
- 实际首帧前，在主线程展示/OnPreDraw 边界复核时间与配置；若失效先取消。若已经绘制，就按已展示处理，不能抹掉事实。

### 11.4 并发和重复回调

Controller 在主线程使用单一事件消费者；SP/MMKV 转到 IO。并发返回的 A/B 也必须经过同一个共享协调器，不允许 A Controller 与 B Controller 各自读到“今天没弹”后同时展示。

整个进程同一时刻最多一个本模块展示事务。首帧、点击和关闭都携带 presentationId；未知或过期 ID 忽略，同一首帧只写一条记录。

如果页面接入同时收到 result 回调和 onResume，最多生成一个 ReturnAttempt。如果按键被连续点击，最多发起一个添加 deeplink，并立即禁止同类型的新展示。

### 11.5 点击添加的严格顺序

用户点击左/右任意添加按钮：

1. 主线程立即锁定该 presentationId 的按钮，并将该类型加入运行时停止集合；从这一刻不再接纳这个类型的新展示。
2. 保存 AddStopRecord；与已知首帧记录/展示日志结束一起在一笔状态写入中合并，不能用一个旧快照覆盖刚写入的次数。
3. 正常情况下保存成功后发起对应快服务 deeplink，一次且仅一次。
4. 无论 deeplink 不存在、被拦截、快服务未安装、路由抛错或添加页返回取消，都不撤销停止标记。
5. 关闭引导；跳转失败可给短提示，但不能恢复“下次继续弹”的状态。
6. 停止标记只作用于当前类型；A 的点击不会写 B 的 addStops。

点击不依赖“真的添加成功”回调，也不需要查询系统是否已有组件。停止原因应命名为 addActionClicked，而不是 installed/everAdded，避免维护者误以为这里有安装检测。

若磁盘失败，运行时仍立即停止，保留未完成日志与同 ID 写入重试，并尽量继续执行用户的添加跳转。跨进程的严格永久保证依赖实际持久化，异常限制见下一节。补写停止记录可以重试，补弹本轮机会绝对不可以。

### 11.6 点击空白区域与系统返回

- 外部空白取消：记录已经首帧展示的一次，不写 AddStopRecord，不退还今天额度。
- 系统 Back 或宿主销毁导致关闭：没有点击添加就不写停止标记；是否计次仍只看首帧是否已经发生。
- 弹窗尚未画出就被取消：不计次，结束日志与本轮。
- 点击添加后发生 onDismiss：只做幂等收尾，不能用普通取消逻辑撤销停止状态。

## 12. 写盘失败、进程死亡和恢复策略

### 12.1 为什么仍需要展示事务日志

只用“show 完再写次数”会存在崩溃空隙：窗口已经出现，记录还没保存，重启后可能再次当成没展示。直接在 show 前加次数又会把没有画出的窗口算进去。

本方案把两个事实分开：

- RESERVED：已经为一次展示保存恢复日志，但还不能确认真实首帧。
- SHOWN：真实首帧已经记录，仍保留本次窗口事务，直到取消或添加点击的结束状态成功保存。

这份日志没有“下次重启继续展示”的含义。重启绝不会恢复引导窗口。

### 12.2 拟议日志字段

| 字段 | 含义 |
|---|---|
| presentationId | 同一次显示过程的唯一身份 |
| guideType | 当前 A/B 类型 |
| phase | RESERVED 或 SHOWN |
| processSessionId | 哪次进程启动创建此日志 |
| createdAtMillis | 预约时间，仅诊断，不充当真实展示时间 |
| shownAtMillis / localEpochDay | SHOWN 时的真实首帧时间信息，和 records 对应项一致 |

记录数量、ID 唯一、phase 与 records 是否匹配，都由严格解码校验。

### 12.3 正常操作和异常操作对照

| 场景 | 正常持久结果 | 失败时处理 |
|---|---|---|
| 本轮频控不通过 | 不创建展示日志，不变更次数 | 机会结束 |
| 展示前预约 | 写 RESERVED | 写失败则不创建窗口，本轮结束 |
| 预约后页面改变/宿主明确拒绝 | 清日志，不新增次数 | 清理失败则保留恢复保护，不另弹 |
| 首帧 | 追加同 ID record，日志转 SHOWN | 保留首帧事实于内存，暂停新展示并补写；不能减次数 |
| 普通取消 | 保留 record，清日志 | 补写收尾；不能以失败为由重新弹 |
| 点击添加 | 保留 record，新增该类型 addStop，清日志 | 立即运行时停止，补写同 ID；无论路由结果都不恢复 |
| 重复回调 | 同 ID 不重复追加/跳转 | 忽略或记录诊断，不改变次数 |
| 数据损坏/未知 schema | 不应出现 | 暂停自动引导，不静默清空用户历史 |

### 12.4 启动时残留日志

下面是异常恢复的保守技术策略，可能导致少弹，须在实现验收时单独覆盖，不能把它宣传为正常产品规则：

- 残留 RESERVED：无法确认此前到底有没有显示、显示在哪一天；为避免破坏共享每日上限，将 sharedQuotaUncertain 置 true，暂停自动引导。不能将预约伪造为一次展示，也不能当成完全没显示。
- 残留 SHOWN 且记录匹配：已知道那次展示，因此保留真实次数/日期；但无法确认用户最后是不是点击了添加而写盘失败，将该类型加入 recoveryHeldTypes。另一类型仍可按自己的状态与共享日额度判断。
- 如果明确停止记录已经保存，优先按真实 addStop 处理，不重复推断。
- 恢复转换本身也要成功写盘；失败就维持暂停。
- 恢复过程不生成 FlowSession/ReturnAttempt，不启动 Dialog，不“把上次没弹完的补上”。

recoveryHeldTypes 表示“结果不确定、保守暂停”，不能伪装为“用户点击添加”。正式版本不提供自动清零恢复；用户清除全部应用数据可以重置。未来若产品要求更积极的故障恢复，需要另设计，不在此次频控语义中暗加一次展示。

### 12.5 严格保证的边界

窗口绘制、用户点击与磁盘持久化不是一个跨系统原子事务。设备断电、磁盘彻底写入失败或存储损坏时，任何纯 SP/MMKV 方案都不能同时保证“每次显示都精确记账”“永不多弹”“永不少弹”。

本方案优先避免多弹：预约日志覆盖显示过程，点击后立即运行时停止，失败不清空数据，并对无法确认的状态暂停。应明确接受这些异常下可能提前暂停的可用性代价。不能用“已经调用 commit/encode”冒充所有物理故障下绝对落盘成功。

**补写账本不等于补弹。** 恢复、重试都只修复计次/停止记录；绝不保留本轮行为机会供将来显示。

## 13. 底部弹窗和设置入口

### 13.1 底部弹窗实现建议

优先适配项目已有的底部弹窗基类或统一弹窗管理器。若项目没有，可用 DialogFragment + XML 并设置底部 Window gravity；若已有 Material 依赖，也可用 BottomSheetDialogFragment。不要为了引导新增一套全局弹窗调度系统。

内容从上到下：

1. 引导标题。
2. 当前组件截图及无障碍描述。
3. 一行两个按钮：**左添加到桌面，右添加到负一屏**。
4. 窗口外部空白区域可取消。

A/B 共用布局，文案、截图、两条快服务 deeplink 由 GuideContentProvider 按类型提供。用 start/end 布局属性适配 RTL，产品若要求中文环境严格左右次序，资源与布局方向策略须保持一致。

小屏、横屏、大字体时内容允许滚动，两个添加按钮保持可点击且不能被导航栏遮挡。Insets、底部手势区域、深浅色、TalkBack 图片描述都属于设备验收。

### 13.2 展示与恢复契约

- Host 同步返回接受/拒绝，不将当前返回机会排到未来再弹。
- 本次首帧可见绘制上报一次 onShown；调用 show/onStart 本身不算次数。
- cancel/关闭保证最终一次 onClosed，避免控制器一直占用展示名额。
- 首帧是本地可观测的近似“已展示”口径，不能证明用户阅读或硬件屏幕已完成合成。
- Fragment 系统恢复若没有当前进程的活跃 presentationId 所有者，在窗口出现前禁止恢复旧引导。
- 当前引导自身出现不能让 HostSnapshot 把自己判为被“其他业务页遮挡”而反复取消/重建。
- 点击失败提示使用短暂提示，不再弹第二个引导窗口；停止状态不撤销。

### 13.3 设置页荣耀判断

设置页数据源构造时调用 DeviceClassifier.isHonorDevice：

- true：插入“添加桌面组件”列表项。
- false：不插入该项。
- 该判断不加到 A/B 自动引导入口。

优先复用正式项目现有荣耀设备识别工具。没有时才集中封装 Build.BRAND / MANUFACTURER 的标准化判断，并按实际目标设备清单验证；不要让不同页面各写一套字符串比较，也不要将所有华为设备默认当作荣耀。历史型号品牌字段存在差异，需用真实设备/现有产品设备分类表验证，避免凭空增加型号白名单。

设置点击只调用快服务 navigator，不写 addStop、record 或展示日志。即使 A/B 已各 3 次或都已点击停止，只要是荣耀设备，手动入口仍可用。

### 14.1 迁移原则

如果旧版只是 Demo，正式功能尚未发布，可以直接以空 V2 状态首次启用。**如果有设备已经运行旧版，需要显式迁移，不能静默清次数。**

建议在首次读取时：

1. 有 state_v2：严格读取；损坏时不能回退 state_v1 当作全新数据。
2. 没有 state_v2 但有合法 state_v1：把旧 records 逐条保留，并按 A/B 分别统计。旧总上限改成新独立上限，但真实历史不丢。
3. 丢弃旧 behaviors，它们在新需求下不再代表资格。
4. 旧版没有 addStop，不能根据历史记录猜用户是否点过添加，初始按未知未记录处理；不虚构点击。
5. 旧 pending 作为未决日志处理，不能直接清除后重新弹。
6. state_v2 成功提交后才认为迁移完成；失败则暂停，不把半迁移数据当成功。
7. 重复迁移保持幂等，presentationId 不变，不重复加记录。
8. 云配切换版本与应用版本配合。回滚旧包时需暂停旧引导或提供兼容策略，防止旧包继续消费过时 state_v1、绕开 V2 停止标记。

旧版 records 没有 zoneId 时，保留其已经存储的 localEpochDay，不拿新时区重新解释旧日期；zoneId 可使用明确的 legacy/unknown 标识用于诊断。

### 14.2 冷启动不会触发的实现保证

冷启动只加载持久频控和配置，注册页面事件并创建空的流程容器。onResume 看到首页但没有本进程的合法返回事务，不会生成 ReturnAttempt。

不能采用“第一次 onResume 跳过、以后都允许”这种布尔写法：旋转、冷恢复、其他外部拉起也可能产生后续 onResume。必须由本轮流程返回事实驱动。

### 15.7 三个关键用例的 Given / When / Then

**用例一：不能在冷却到期后突然弹。**

- Given：A 展示过一次，24h 冷却尚差 1 分钟；当前用户完成合法搜索并原栈返回。
- When：本轮因冷却失败，随后推进 FakeClock 两分钟，仅发送时间/配置/页面可见更新。
- Then：showCalls 始终为 0，且没有待评估 ReturnAttempt。
- When：再输入一整套新的合法搜索和原栈返回事件。
- Then：只调用一次 show；首帧前次数不变，首帧后 A 次数加一。

**用例二：添加链接失败也停止对应类型。**

- Given：A 窗口已首帧显示，FakeNavigator 固定抛异常。
- When：点击左侧添加按钮，然后模拟 onDismiss 和应用重启。
- Then：A 的 addStop 保留；A 新行为不再展示；B 的 stop 未改变。B 今天仍可能因 A 已展示受到共享日限制，不能把这个原因误认为 B 被永久停止。

**用例三：清栈不是原栈返回。**

- Given：路径 H→S→R→D，R 已完成关键节点。
- When：D 通过 CLEAR_TOP 回 H，同时旧 result 和 H.onResume 都发生。
- Then：flow 被标记无效；重复回调也不能生成 ReturnAttempt；showCalls 为 0。

## 16. 风险点与对应措施

| 优先级 | 风险 | 后果 | 设计措施/验收 |
|---|---|---|---|
| P0 | 保留 V1 长期 behaviors 或到期 timer | 用户没做新行为却突然弹 | 删除此语义，Q01～Q05、P11 |
| P0 | 把同类页面当同一个实例 | 在错误首页/二级页弹 | containerId + taskId + processSessionId，N17/N19 |
| P0 | 只在 onResume/result 中弹，不验证原栈 | 清栈、外部拉起也弹 | 正常返回关系 + 一次可见配对，N18/Q08 |
| P0 | 按控件/URL 文字猜搜索成功 | 暗词落详情、游戏页被误算 | 最终业务页确认 + 合法直接边，N05/N06/N09 |
| P0 | A/B 各自独立展示控制器 | 同一天并发弹两次 | 一个共享串行控制器与事务日志，C04 |
| P0 | 使用总记录 3 次作为全局上限 | A 用完导致 B 永久不能弹 | 类型统计与共享日额度分离，F07 |
| P0 | 点击后等待添加成功才 stop | 跳转失败又继续打扰 | 点击立即停止，C08～C12/P07 |
| P0 | 旧关闭回调覆盖新状态 | addStop 丢失或多计数 | presentationId 关联、原子状态更新 |
| P1 | 中途页面未接入或绕过路由器 | 无法证明原栈 | 未知路径本轮失效，补全公共页面适配 |
| P1 | singleTask、NEW_TASK、CLEAR_TOP 等改变返回语义 | 结果回调缺失/提前或栈被重排 | 不依赖名称推断；按真实任务/实例变化取消流程 |
| P1 | Promise 持有旧 Activity 或回调在线程池 | 泄漏、在错误窗口弹、线程异常 | 生命周期绑定、主线程交接，审查现有封装 |
| P1 | 配置重建和进程恢复混淆 | 恢复了旧资格或误删仍有效流程 | 逻辑实例 + 新进程 nonce，Q09/Q10 |
| P1 | 预测返回取消或两个生命周期乱序 | 提前出栈/重复弹 | 返回提交与父页可见配对，N22/Q06 |
| P1 | 写盘挂起期间页面离开/云配变动 | 旧条件仍启动窗口 | 最新快照复核、单调失效标记，C05/C06 |
| P1 | 首帧/点击与磁盘不能原子化 | 极端情况下次数/停止结果不明 | 展示日志与保守暂停，明确可能少弹 |
| P1 | 存储损坏/迁移失败被当成首次使用 | 重新打扰已停止用户 | 严格解码、幂等迁移、不静默清空 |
| P1 | 设备时钟、时区变化 | 冷却或自然日判断异常 | 分开计算，回拨拒绝，不自动补弹 |
| P1 | 正式工程自动备份恢复 SP | 用户重装后历史又回来 | 文件备份排除并设备迁移验收 |
| P1 | 品牌识别只凭随意字符串判断 | 设置项误显/误隐藏 | 复用设备分类工具，真实机型验证 |
| P1 | 把仅荣耀条件复制到自动模块 | 非荣耀自动引导被错误屏蔽 | U07 + F18 |
| P2 | 底部 Insets、大字体、横屏未适配 | 按钮遮挡、截图压缩 | XML 滚动和设备覆盖，U06 |
| P2 | 记录用户搜索词/内容作为调试信息 | 多余数据采集 | 仅记录枚举、随机 ID、时间、拒绝原因 |

严格原栈识别是否可以低成本接入，取决于正式项目现有页面/返回管理基础设施。这是需要在实施阶段验证的工程风险；文档没有假装 ARouter 自动提供了完整返回栈，也没有把增加全项目隐藏 API 反射当作解决方案。

## 17. 诊断信息与开发验收

### 17.1 推荐诊断字段

记录 flowId、triggerKind、guideType、ownerContainerId、milestonePageId、returnReason、attemptId、presentationId、当前次数、拒绝枚举和存储异常类别。页面 ID 使用随机身份，不带搜索词、书签标题、用户账号或资讯正文。

推荐拒绝原因：

- INVALID_FLOW：没有合法本轮或关键节点。
- NON_STACK_RETURN：没有沿原栈返回。
- OWNER_MISMATCH：承载实例/任务不匹配。
- ATTEMPT_CONSUMED：重复返回。
- HOST_NOT_READY：当前页面无法即时展示。
- DISABLED：云配关闭/非法。
- TYPE_STOPPED：该类型点击添加停止。
- TYPE_LIMIT：该类型已三次。
- SHARED_DAILY_LIMIT：今天 A/B 已展示一次。
- TYPE_COOLDOWN：该类型冷却未到。
- CLOCK_ROLLBACK：时钟/日期早于已知历史。
- RECOVERY_HOLD / STORAGE_ERROR：结果不确定或存储故障。

日志必须能区分“本轮没有满足行为”和“满足但被频控拒绝”。两者都不会保留未来资格，但排查原因不同。

### 17.2 实施顺序与完成标准

1. **先改纯规则和数据协议。** 每类型上限、共享日额度、enable、忽略 third、点击停止，以及旧数据迁移。
2. **实现本轮流程跟踪器。** 用假的页面事件验证搜索、扫一扫、我的、两种 AI 流程及正常/异常返回。
3. **接入正式页面与 ARouter。** 先跑通一个搜索链路，再补入口差异、同 Activity Tab 和二级 AI；必要时适配已有 Promise。
4. **实现即时返回评估。** 证明冷启动、到期、云配更新、普通 onResume 都无法补弹。
5. **实现展示日志与点击停用。** 覆盖首帧、取消、异常和进程中断。
6. **接底部 XML 和设置列表。** 真实截图与快服务链接由项目现有资源提供，不编造 URI。
7. **完成新单测和真机链路验收。** 构建 Debug/混淆 Release、跑 Lint；正式机型验证返回、快服务、设备分类。
8. **更新迁移/验收文档。** 把旧版案例中“无需新行为可再次弹”“AI 频道 B→A 补位”“AB 总三次”等删除或标为历史。

开发完成的最低判据是：每一类正向路径能在正确位置产生一次即时评估；所有负向路径、冷启动及失效机会不会补弹；次数/停止与共享每日额度符合规则；点击链接失败仍保持停止；旧数据迁移不复活旧资格。
